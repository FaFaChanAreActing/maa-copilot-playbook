# 从参考视频到可复现 Copilot JSON

本文是 [README](../README.md) 的完整展开，适合已经做过一两次作业、但坐标和技能轴还不稳定的制作者。

## 0. 先定义“做完”的标准

一份作业只有同时满足下面三条，才算做完：

1. **坐标可复现**：每个落点都在可部署格上，朝向不会打空。
2. **技能轴可复现**：作业里的 `skill` 和 `skill_usage` 与账号实际携带的技能一致。
3. **结果可验收**：不只是“MAA 任务完成”，而是游戏里战斗胜利 / 三星结算。

只做到“JSON 能导入、干员能落地”不算完成。

## 1. 制作流程总览

```text
参考视频
  ↓ 抽帧 + 字幕/口播
关键帧与部署顺序
  ↓ 查 tile JSON
可用落点与格型
  ↓ 对齐账号技能
干员 / 技能 / 技能用法
  ↓ 写 actions
Copilot JSON
  ↓ 演习首跑
失败归因 → 单变量修正
  ↓ 实战验收
发布到作业站
```

每一步都要留下可回看的记录：帧号、坐标、格型、技能序号、试跑 taskid。不要只凭记忆。

## 2. 参照系：三套坐标不要混用

### 2.1 MAA 坐标

MAA Copilot 的 `location` 是 `[x, y]`：

- `x`：从左往右，0 开始；
- `y`：从上往下，0 开始；
- 地图左上角是 `(0,0)`。

写 JSON 时只认这一套。

### 2.2 游戏网格与 PRTS.Map

PRTS.Map 可以切换坐标显示模式。普通模式与 MAA 模式的数字可能不同。最稳妥的做法是：

1. 用 MAA 实战生成一张 `debug/map/<时间>_<stage>.jpeg`；
2. 在图上找到已知地标（蓝门、红门、高台边缘）；
3. 用三个不共线的点拟合网格；
4. 再回到 PRTS.Map 交叉验证。

如果两张图的坐标对不上，以 MAA debug map 为准。

### 2.3 视频帧

视频帧只适合回答三类问题：

- 谁先落地、谁后落地；
- 大致在左/右/上/下哪个区域；
- 朝向和技能特效。

不要从视频帧直接量精确坐标。视频有透视、缩放、UI 遮挡，误差通常大于一格。

## 3. 格型：先读 tile JSON，再写落点

MAA 的关卡 tile 文件通常位于：

```text
resource/Arknights-Tile-Pos/<stage>-<level>.json
```

结构要点：

```json
{
  "tiles": [
    [ { "buildableType": 0, "heightType": 0 }, ... ],
    ...
  ]
}
```

- `tiles[y][x]`：先 y 后 x。
- `buildableType`：
  - `0`：不可部署；
  - `1`：近战位；
  - `2`：远程位。
- `heightType`：
  - `0`：地面；
  - `1`：高台。

### 3.1 为什么“看起来能放”的格子不能放

地图美术里有很多“平台边缘、装饰地板、楼梯口”，在 tile JSON 里可能是 `buildableType: 0`。这类格子无论等多久、换什么朝向都不会落地，表现为：

- MAA 日志显示已执行 `Deploy`；
- 游戏里干员没有出现；
- 费用没有被扣，或者部署预览根本不显示。

遇到这种情况不要继续等，直接查 tile JSON。

### 3.2 落点核对表

每个落点都写一行：

```text
operator | location | buildableType | heightType | direction | note
```

示例：

```text
凛御银灰 | (6,6)  | 1 | 0 | Down  | 中路回费
结城理   | (1,4)  | 1 | 0 | Up    | 左上切位
圣聆初雪 | (10,3) | 2 | 1 | Down  | 右侧下层高台
遥       | (10,2) | 2 | 1 | Down  | 初雪正上方
斩业星熊 | (3,1)  | 1 | 0 | Right | 左上阻挡
```

这张表就是后续改坐标时的“真相源”。

## 4. 视频拆解：把口播翻译成动作

### 4.1 先抓顺序，不抓像素

口播里的“桃子↓、结城理↑、初雪→、遥↓、星熊→”是顺序和朝向，不是坐标。先把顺序写成动作列表：

```text
1. 先锋 Down
2. 近战 Up
3. 术师 Right
4. 近战开技能
5. 辅助 Down
6. 重装 Right
7. 挂机
```

### 4.2 再定位每个动作

用关键帧确认“在哪个区域”，再用 tile JSON 和 debug map 找精确格。定位时优先找唯一地标：

- 红门 / 蓝门；
- 高台缺口；
- 地图边缘的柱子；
- 敌人出生点。

### 4.3 识别“口播没说的动作”

视频里经常有口播没提、但实际必须做的动作：

- 某个干员第一次技能是手动开；
- 某个干员需要等费用；
- 某个干员要撤退再部署；
- 某个干员技能只开一次。

这些动作如果不写进 `actions`，作业就会出现“干员都落地了，但输出不够/漏怪”。

## 5. 技能轴：作业里最容易错的部分

### 5.1 `skill` 是技能序号，不是技能名

```json
{ "name": "圣聆初雪", "skill": 2, "skill_usage": 1 }
```

表示使用该干员的第 2 个技能。账号实际带 3 技能时，必须改成 `3`，否则会出现：

- 作业以为在开 2 技能，游戏实际是 3 技能；
- 技能轴完全错位；
- 阵法术师类干员长期不攻击。

### 5.2 `skill_usage` 的四种常见写法

| 写法 | 含义 | 适用 |
|---|---|---|
| `0` | 不自动使用 | 需要精确手动轴的干员 |
| `1` | 好了就用 | 大部分常规技能 |
| `2` + `skill_times` | 用指定次数 | 只需要开一两次的技能 |
| `SkillDaemon` | 持续托管 | 只对 `skill_usage: 1` 生效 |

### 5.3 手动轴怎么写

```json
{ "type": "Skill", "name": "结城理", "pre_delay": 2400, "timeout": 10000 }
```

- `pre_delay`：部署后延迟多少毫秒再尝试开技能；
- `timeout`：最多等多久；
- 对应干员必须设 `skill_usage: 0`，否则会被自动技能抢走。

### 5.4 技能轴核对清单

- 每个干员的 `skill` 与账号实际一致；
- 该手动的没有被 `skill_usage: 1` 自动开掉；
- 该自动的没有被写成 `0` 导致一直不开；
- `SkillDaemon` 放在所有需要手动轴的干员之后；
- 第一次技能的时间点与视频关键帧对得上。

## 6. JSON 结构与动作顺序

一个最小可用的 Copilot JSON：

```json
{
  "version": 3,
  "stage_name": "act46side_ex08",
  "minimum_required": "v6.7.0",
  "difficulty": 3,
  "opers": [
    { "name": "凛御银灰", "skill": 2, "skill_usage": 1 },
    { "name": "结城理", "skill": 3, "skill_usage": 0 }
  ],
  "actions": [
    { "type": "SpeedUp" },
    { "type": "Deploy", "name": "凛御银灰", "location": [6, 6], "direction": "Down" },
    { "type": "Deploy", "name": "结城理", "location": [1, 4], "direction": "Up" },
    { "type": "Skill", "name": "结城理", "pre_delay": 2400, "timeout": 10000 },
    { "type": "SkillDaemon" }
  ],
  "doc": {
    "title": "示例作业",
    "details": "参考视频、阵容、部署顺序、注意事项。"
  }
}
```

### 6.1 动作顺序原则

1. `SpeedUp` 放最前，减少等待。
2. 先放回费/先锋，再放输出。
3. 需要特定击杀数或费用条件的技能，放在对应部署之后。
4. `SkillDaemon` 放最后，避免它提前接管手动技能。
5. 不要在 `SkillDaemon` 之后再写 `Skill`，否则可能不生效。

### 6.2 `doc` 写什么

作业站的展示主要看 `doc.title` 和 `doc.details`。建议包含：

- 参考视频链接；
- 阵容与替代关系；
- 部署顺序；
- 技能配置；
- 关键注意事项；
- 作者署名（可选）。

不要把调试过程、内部吐槽、账号信息写进 `doc.details`。

## 7. 首跑与失败归因

### 7.1 首跑必须用演习

演习不消耗理智，失败成本低。首跑只验证“动作链是否按预期执行”，不追求一次三星。

### 7.2 看三个东西

1. **MAA 日志**：`asst.log` 里的 `CopilotAction`、`Deploy`、`UseSkill`、`unknown oper`。
2. **debug map**：`debug/map/*.jpeg`，确认干员实际落地位置。
3. **游戏录像/截图**：确认击杀数、生命值、技能是否真的开了。

### 7.3 常见失败与归因

| 现象 | 可能原因 | 处理 |
|---|---|---|
| 干员一直不落地 | 落点 `buildableType: 0` | 查 tile JSON，换格 |
| 日志 `unknown oper N` | 战斗卡序第 N 张不是你以为的干员 | 核对卡序，不改名字先核对 |
| 日志 `Group not found` | 作业引用了不存在的干员组 | 检查 `groups` 或删掉组引用 |
| 干员落地但不攻击 | 阵法术师未开技能 / 技能序号错 | 核对 `skill` 和 `skill_usage` |
| 前期漏怪、生命值下降 | 输出轴太晚 / 技能没开 | 提前技能或换输出位 |
| 费用不够，动作被跳过 | 部署顺序或回费不足 | 调整先锋/部署顺序 |
| MAA 显示任务完成但未三星 | 只跑了动作链，未确认结算 | 看结算画面，必要时重跑 |

### 7.4 单变量修正法

失败后不要一次改三个地方。按下面顺序逐个排除：

```text
坐标 → 朝向 → 技能序号 → 技能时机 → 阵容替换
```

每改一项，记录：

```text
时间：
taskid：
改动：
现象：
结论：
```

## 8. 坐标案例：OS-EX-8

地图 13×9，`tiles[y][x]`。本作业使用的落点全部通过 tile JSON 校验：

```text
凛御银灰  (6,6)  type=1  Down
结城理    (1,4)  type=1  Up
圣聆初雪  (10,3) type=2  Down
遥        (10,2) type=2  Down
斩业星熊  (3,1)  type=1  Right
```

已确认不可用的典型格：

```text
(4,4)  buildableType=0  tile_floor
(2,6)  buildableType=0  tile_forbidden
(6,5)  buildableType=0
(6,4)  buildableType=0  tile_end
```

这些格子在截图里可能像地板或高台，但 tile JSON 里就是 0。不要靠“再等等”解决。

## 9. 发布到作业站

发布前确认：

- `stage_name` 正确；
- `difficulty` 正确；
- `doc.title` 简洁，不超过平台习惯；
- `doc.details` 包含参考视频、阵容、部署顺序、注意事项；
- 作业已在演习或实战中至少跑通一次；
- 没有账号信息、UID、邮箱、本地路径。

作业站会校验 JSON 和表单。看到“JSON 验证：通过 / 表单验证：通过”再发布。

## 10. 最终验收清单

- [ ] 每个落点都查过 `buildableType`。
- [ ] 每个朝向都不会打空。
- [ ] 每个 `skill` 与账号实际一致。
- [ ] 手动技能写 `skill_usage: 0`，并配 `Skill` 动作。
- [ ] `SkillDaemon` 在最后。
- [ ] 演习首跑完成。
- [ ] 实战/结算确认战斗胜利。
- [ ] `doc.title` 与 `doc.details` 已清理。
- [ ] 作业站发布成功，记录作业 ID。

做到这里，才算一份可以交给别人抄的作业。
